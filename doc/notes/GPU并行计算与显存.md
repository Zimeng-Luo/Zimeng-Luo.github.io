# 理解 GPU：并行计算、线程组织与显存瓶颈

GPU 擅长在大量数据上执行相似计算，常用于渲染、矩阵运算和神经网络。但“核心更多”不意味着所有程序都会更快，任务结构和数据搬运往往更重要。

## CPU 与 GPU 优化目标不同

CPU 重视低延迟、复杂控制流与通用系统能力，GPU 通过大量并行执行资源和较高存储带宽提升吞吐。两者核心的结构不同，不能直接按数量比较性能，也不能把 CPU 核心数固定为某个典型数字。

GPU 可以执行分支、整数和浮点等多种指令，不是只会做四则运算的硬件。分支多、数据依赖强或任务很小时，GPU 仍可能因调度和传输开销不划算。

## 硬件结构与软件线程分开看

GPU 包含多个 SM（流多处理器），SM 内有不同计算、调度和存储资源。具体数量、缓存容量和 Tensor Core 能力依架构与产品而变，不能用一个型号的规格代表所有 GPU。

CUDA 编程的组织方式是：

| 软件单位 | 含义 |
| --- | --- |
| Thread | 一个逻辑执行实例 |
| Warp | NVIDIA 常见实现中由 32 个线程组成的调度分组 |
| Block | 一组可使用共享内存及块内同步的线程 |
| Grid | 一次 kernel 启动的全部线程块 |

线程是软件执行上下文，不与某一个 CUDA 硬件核心永久一一绑定。Warp 也不是“内部装着 32 个固定核心”的硬件容器；调度器把指令发给执行单元，SM 通常交错执行多个驻留 Warp 来隐藏等待。

## SIMT 与分支分歧

SIMT 允许程序按线程编写，而硬件按 Warp 组织许多执行操作。当同一 Warp 的线程进入不同分支，可能需要分阶段执行并屏蔽暂不参与的线程，降低利用率。

较新的架构具备独立线程调度等能力，但不意味着分支代价消失，也不能省掉程序所需的显式同步。SIMT 不是在某一年突然替代 SIMD 的简单时间分界，两者是不同层次的执行抽象。

## 显存容量与带宽解决不同问题

容量决定能否放下模型、激活和数据；带宽决定每秒能搬运多少数据。计算单元等待访存时，继续增加计算能力未必有效。

寄存器、共享内存、L1/L2 缓存与显存形成不同层级。共享内存通常用于块内协作，缓存由硬件按相应机制管理，两者不能因为都在 SM 附近就当成同一种资源。

连续线程访问连续地址有助于合并访存。CPU 与 GPU 之间的数据传输又可能受 PCIe 等互连限制，因此应尽量减少频繁来回搬运小块数据。

GDDR 和 HBM 面向不同封装与带宽需求。HBM 通过堆叠和较宽接口提供高带宽，具体能耗和性能还依系统设计。PAM3/PAM4 是链路信号编码，不表示 GPU 的计算逻辑变成三进制或四进制。

## Tensor Core 也有适用条件

Tensor Core 面向某些矩阵乘加及支持的数据类型，常用于深度学习。实际收益受矩阵大小、布局、精度和库实现影响。低精度吞吐高，也需要验证数值误差与最终任务质量；FMA 将乘加融合时的舍入行为还与分别计算不同。

## 判断瓶颈的三个问题

1. 并行度是否足够，任务之间是否有强依赖？
2. 每搬运一次数据做了多少计算，主要受计算还是带宽限制？
3. 时间花在 kernel、同步还是主机与设备传输上？

用这些问题解释 GPU，比背某张显卡的晶体管数量更能迁移到其他设备。进一步可参考 NVIDIA 的 CUDA Programming Guide 和 CUDA Best Practices Guide，按实际架构查规格与优化约束。
